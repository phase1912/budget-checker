# Solution concept: receipt-crud-2 — Receipt create, read, update, delete

This follows from the approved problem brief (docs/sdlc/receipt-crud-2/01-problem/problem_brief#75.md): the receipts tracker's own API cannot put a receipt into its own table. `backend/app/routers/receipts.py` holds exactly three handlers — `list_receipts` (lines 45–66), `upload_receipt_photo` (69–111), `get_receipt_photo` (114–130) — and no create, read-one, update or delete, so the list endpoint lists rows nothing can produce. The gap is deliberate: the prior run `docs/sdlc/receipts6/` scoped receipt CRUD out explicitly (its `baseline.md` line 27: "deliberately rejected by the earlier foundation process"); this goal reverses that settled decision, and the person has now confirmed the reversal at chosen-direction (settled_question#94).

What constrains every option here, from reading the code (settled_question#83): the `Receipt` model (backend/app/models.py lines 55–72) is complete — id with a `uuid4` default, `user_id`, `amount Numeric(12,2) nullable=False`, `description` nullable, `created_at` default — so no option needs a migration, and the photo cascade (`photo` relationship, `cascade="all, delete-orphan", passive_deletes=True`, plus `ondelete="CASCADE"` on `receipt_photos.receipt_id`) makes delete-with-photo fall out of `db.delete(receipt)` for free. The module already contains the idioms to copy: `_get_owned_receipt` (line 35) for owner-or-uniform-404, `_NOT_FOUND_DETAIL` (line 23), and the validate-then-commit transaction pattern in `upload_receipt_photo`. One genuine fork existed at drafting time: the receipts list endpoint returns raw dicts with `response_model=None`, while the budgets module uses typed Pydantic schemas (`BudgetCreate` / `BudgetSummaryResponse`, backend/app/schemas.py lines 45–61). Whichever way create/read/update serialize, the list endpoint's exact answer is frozen by the goal.

## Options considered

### Option A — Do nothing (or the smallest possible thing: keep hand-inserting rows)
Record that the reversal of receipts6's line 27 stands, and receipts keep entering the table the way the receipts6 acceptance path evidently did — direct database/session manipulation, as `backend/tests/test_receipts.py`'s own `_make_receipt` helper does today. Cost: zero. Gives up: the entire outcome — the product remains a receipts tracker in which the API cannot fill the table every other feature reads (problem_brief#75, cost of inaction). Changing our mind later costs nothing, since nothing was built, but nothing improves while we wait either.

### Option B — Four additive endpoints inside the existing router, following the receipts module's own idiom
POST `""` (create), GET `/{receipt_id}` (read one), PATCH/PUT `/{receipt_id}` (update amount/description), DELETE `/{receipt_id}` (delete), all in `backend/app/routers/receipts.py`, each going through `_get_owned_receipt` and raising the uniform `_NOT_FOUND_DETAIL` 404, each committing via `get_db` exactly as the photo endpoints do. Serialization follows the module's existing precedent: raw dicts, `response_model=None`, so the file stays self-consistent and the frozen list endpoint shares its shape. Delete is `db.delete(receipt)`; the declarative cascade takes the `ReceiptPhoto`. Create does NOT take a photo — the existing RCP-15 one-photo upload endpoint stays the only path. Cost: well inside the one-day appetite (settled_question#88) — four thin handlers plus tests extending the existing 410-line suite in `backend/tests/test_receipts.py`, which already anticipates the cascade (`test_deleting_receipt_takes_its_photo_with_it`, line 310). Gives up: request validation and response typing — an amount of `"abc"` fails only at the database layer, and the OpenAPI schema for the new endpoints is untyped. Changing our mind later is cheap: adding schemas later touches only these four handlers.

### Option C — Same four endpoints, but typed Pydantic schemas in `backend/app/schemas.py`, following the budgets precedent
Identical routes and semantics, but create/update accept typed request models (amount must be a finite number, description optional) and read returns a typed response, the way `BudgetCreate` (schemas.py line 49) works for budgets. Cost: a little more than B — two new schema classes, validation rules to decide (a real question the budgets7 review already flagged once: `BudgetCreate.target_amount` as a plain `float` let NaN and Infinity through, per `docs/sdlc/budgets7/07-review/review_report#283.md`), and tests for the validation paths. Still inside a day. Gives up: file-local consistency (receipts and budgets would then serialize differently from the receipts list endpoint, which must stay raw); slightly more surface for a one-maintainer project. Changing our mind later is equally cheap.

Two directions are not offered as options because the constraints rule them out outright: anything touching the `receipts` schema (soft-delete column, audit table — needs a migration the goal forbids, settled_question#87), and photo-on-create (duplicates the RCP-15 upload path and moves binary handling into a JSON endpoint, which settled_question#83 ruled expensive for no stated need). Neither is a reasonable-engineer option under problem_brief#75's constraints.

## Chosen approach

The person chose Option B (settled_question#94): four endpoints in the existing receipts router, reusing the ownership check the module already has, with deletion leaning on the cascade the Receipt–ReceiptPhoto relationship already declares rather than deleting the photo by hand. The receipts6 scoping reversal is thereby confirmed as deliberate — the open question carried from the change brief and the problem brief closes here.

What that means, at the level this stage owes: four new handlers are added to `backend/app/routers/receipts.py` — create, read-one, update (amount and/or description) and delete — each copy the module's own patterns rather than inventing new ones. Create stamps `user_id` from the authenticated caller and lets the model default the id and `created_at`; it takes amount and optional description and nothing else, and no photo — the RCP-15 one-photo upload endpoint remains the only way to attach one. Read-one, update and delete resolve their receipt through `_get_owned_receipt`, so a nonexistent id and someone else's receipt both get the same `_NOT_FOUND_DETAIL` 404 the photo endpoints already return, with no "not yours" signal. Update touches only amount and/or description. Delete is `db.delete(receipt)`; the declarative cascade removes the `ReceiptPhoto` — the mechanism `test_deleting_receipt_takes_its_photo_with_it` (backend/tests/test_receipts.py line 310) already pins at the model layer, so the new work is exercising it through HTTP, not building a new one. Serialization follows the module's raw-dict idiom (`response_model=None`), keeping the file self-consistent and the frozen list endpoint untouched in shape. The list endpoint, the photo endpoints and `_get_owned_receipt`'s contract do not move; no file outside this router and its tests changes.

## Why not the alternatives

**Option A (do nothing)** was the honest baseline, and here it was not absurd: the gap exists because a whole prior process deliberately put it there (`docs/sdlc/receipts6/baseline.md` line 27), and the evidence for the change is the shape of the code, not a ticket count (problem_brief#75, Evidence). The person declined it — they confirmed the reversal of receipts6's scoping decision is what they want, and named the reuse of the existing ownership check and cascade as what made the additive direction preferable. Waiting buys nothing: the cost of inaction is the product's core loop being impossible through its own API, and the fix is a day inside the appetite.

**Option C (typed schemas throughout)** nearly tied and remains a reasonable engineer's choice. It buys input validation and a typed OpenAPI contract for four public endpoints — real value as the public surface grows. The person did not choose it, preferring to reuse what the module already has rather than introduce schema classes; its validation is also where the one prior bug in this exact spot lives (the budgets7 NaN finding), it makes the receipts module internally inconsistent with its own frozen list endpoint, and the extra surface is more than a one-day, one-maintainer appetite wants to carry for endpoints whose only consumer today is the API's own tests. It stays one small step away from the chosen approach: add two schema classes and wire them into create/update.

## Constraints

All from settled_question#87 (bohdan) and the goal: backend only, using the stack already in the repository (FastAPI, SQLAlchemy, pytest). No migration — the `receipts` table is used exactly as it stands. The existing list endpoint's response must not change. The frontend must not be touched. From settled_question#88 (bohdan): appetite is small, a day at most. From settled_question#89 (bohdan): mostly reversible — four new endpoints in an existing router — except that deleting a receipt is not reversible for the user, which is why it must be theirs to ask for and theirs alone. The chosen approach respects all of these: it is four additive handlers in one backend router file, models.py does not move, and `list_receipts` is untouched.

## Assumptions

- The reversal of the receipts6 scoping decision is intentional — *checked now*: the person answered it at chosen-direction (settled_question#94) by choosing the additive CRUD direction.
- The `Receipt` model needs nothing added — *checked now*: the model at backend/app/models.py lines 55–72 already has id default, user_id, amount, description, created_at, and the cascade; `create_all` against the live database creates nothing new, which is the point.
- The delete cascade removes the photo through the ORM path the HTTP handler would use — *checked now at the model layer*: `test_deleting_receipt_takes_its_photo_with_it` (backend/tests/test_receipts.py line 310) runs `db.delete(receipt)` and asserts zero `ReceiptPhoto` rows remain; the HTTP-path version is a new test, not a new mechanism.
- The uniform not-found semantics extend unchanged to all four operations — the goal states it in words and the person reaffirmed it ("reusing the ownership check the module already has", settled_question#94); the response shape is copied from the photo endpoints (`_get_owned_receipt` + `_NOT_FOUND_DETAIL`). Exact contract detail settles at requirements.
- Create accepts amount and optional description and nothing else; no photo-on-create — the problem brief left the create shape open (problem_brief#75, open questions 2–3); this concept proposes the minimal shape consistent with the model, which the person's answer did not contradict.
- Exactly one account exercises this through the API only — carried from problem_brief#75. *Only discoverable later*, and low-stakes.

## Risks

- **Untyped create/update lets bad input reach the database** (a non-numeric amount surfacing as a 500 rather than a 422), the same failure class the budgets7 review documented for `BudgetCreate`. Early signal: the new test suite — a malformed-body test per endpoint makes it visible the day it lands; if it bites, the C-style schemas are the ready-made fix.
- **Delete is irreversible for the user** (settled_question#89). The constraint is that only the owner can trigger it and the uniform 404 hides others' receipts; no confirmation step is proposed. Early signal: acceptance scenarios at the next stage decide deliberately whether any guard belongs there.
- **The existing list endpoint drifts.** Any temptation to make create return "the same shape as the list entries" must not change what GET `""` returns. Early signal: the frozen list tests keep passing unmodified; the code review lens checks the diff never touches `list_receipts`.

## Out of scope

Carried from problem_brief#75 (Out of scope): no frontend work (`ReceiptsStore`, `api/client.ts` untouched); no bulk import; no currency handling beyond the `Numeric(12,2)` the column already has; no change to the photo endpoints beyond what deleting a receipt requires of them. Newly excluded by this choice: any schema change or migration (no soft-delete column, no audit/history table, nothing in `backend/app/models.py` moves); photo-on-create and any inline-photo field (the RCP-15 one-photo upload endpoint remains the only way to attach a photo); multi-user or admin semantics beyond the existing owner-only rule; and any change to `_get_owned_receipt`'s contract or `_NOT_FOUND_DETAIL`.
