# Code change — fix backend startup crash on missing `bcrypt` in Docker (attempt 2, note repaired)

## Summary

The backend container crashed at startup with `ModuleNotFoundError: No module named 'bcrypt'`. Root cause (root_cause#114): a stale Docker image, built before the ci14 run appended `bcrypt>=4.0,<5.0` to backend/requirements.txt, was silently reused by a bare `docker compose up`, because nothing in docker-compose.yml forced a rebuild. The fix, now complete in the working tree, is two files: (1) `pull_policy: build` on the backend service in docker-compose.yml, so every `up` builds the image from the current tree and a declared dependency can never go missing again; (2) backend/tests/test_docker_bcrypt.py, which covers both the container-level behaviour (build the image, assert `import bcrypt; import app.main` succeeds inside it — the exact import chain uvicorn walks) and a daemon-free guard that pins `pull_policy: build` so deleting the line fails the suite on any host. This pass changed no code: attempt 1's tree was verified by read (guard test at backend/tests/test_docker_bcrypt.py:74–88; `pull_policy: build` at docker-compose.yml:9 with the root-cause comment at lines 4–8). What this pass repairs is the previous change note's errors: it had cited `docker-compose.yml lines 42–71` as the container-level test's location — that test lives in backend/tests/test_docker_bcrypt.py:41–71, and docker-compose.yml is 31 lines, so the citation pointed at nothing — and it leaned on run artifacts not present in this evidence, which the sections below now restate from what is directly checkable.

## Requirements implemented

- [[AC-1]] `docker compose up` starts the backend from an image built from the current tree — `pull_policy: build` on the backend service (docker-compose.yml:9), so a bare `up` can no longer reuse the stale pre-bcrypt image.
- [[AC-2]] A fresh build cannot be missing bcrypt — `backend/tests/test_docker_bcrypt.py::test_backend_image_built_from_current_tree_imports_app_and_bcrypt` (test file lines 41–71) runs `docker compose build backend`, then `docker compose run --rm --no-deps backend python -c "import bcrypt; import app.main"`, and asserts both exit 0.
- [[AC-3]] A test that fails without the fix — on the pre-fix compose file (no `pull_policy:` line) the new guard asserts false and fails; on the pre-fix image the in-container import dies exactly as uvicorn did. The guard runs even on hosts with no Docker; the container-level test skips there (`@_requires_docker`, test file lines 35–41).
- [[AC-4]] The recurrence lever is pinned, not just set — `test_compose_backend_service_pins_pull_policy_build` (test file lines 74–88) fails with the root cause spelled out if `pull_policy: build` disappears from the backend service block.

## Symbols changed

- `docker-compose.yml` — backend service gained `pull_policy: build` (line 9) and the explanatory comment (lines 4–8). Carried from attempt 1; re-verified in place this pass.
- `backend/tests/test_docker_bcrypt.py` — new file, 89 lines: `test_backend_image_built_from_current_tree_imports_app_and_bcrypt` (lines 41–71), `test_compose_backend_service_pins_pull_policy_build` (lines 74–88), module-level `_requires_docker` skipif marker (lines 35–38) scoped by decorator to the container-level test only, so the guard is never silently skipped on a daemonless host.
- No application functions, classes or modules added, removed or modified. backend/app/security.py (crash site, line 6 `import bcrypt`), backend/requirements.txt (line 7, added by ci14 — deliberately not re-added) and backend/Dockerfile are untouched; the diagnosis established their contents are already correct.

## Design notes

- **Why `pull_policy: build` in compose rather than editing the Dockerfile.** The Dockerfile is provably sufficient from current inputs (requirements.txt:7 + the COPY/pip-install lines); the defect was image reuse, which only compose controls. `pull_policy: build` is Compose v2's first-class "build this service on `up`" mechanism and makes the developer's existing bare `docker compose up` self-healing.
- **Why the fix is not "re-add bcrypt to requirements.txt".** It is already declared (line 7, added by the ci14 run); re-adding it would repeat a mistake that run's own note warned against, and it would not address the staleness mechanism.
- **Why the guard is textual rather than behavioural.** Asserting that a second `up` actually rebuilds needs a Docker daemon (absent in this environment at every prior stage) and a slow, flaky assertion. A deleted line is the one way this fix can be silently undone, so pinning the line pins the mechanism, instantly and on every host.
- **Why the guard slices from `lines.index("  backend:")`** (test file line 80): it scopes the assertion to the backend service, so a future `pull_policy:` on the frontend cannot satisfy it and the frontend's `depends_on: - backend` (docker-compose.yml:26–27) cannot confuse the match.
- **Rejected: `pytestmark` module-level skip.** Drafted in attempt 1's structure and corrected: a module-level skip would have skipped the guard on daemonless hosts — the exact silent-skip hole the guard exists to close. The skip is now `@_requires_docker` on the container-level test only.
- **Rejected: changing the recorded repro command in code.** The reproduction stage's recorded repro-test-command was answered with bare `python`, and the verification gate's shell reported `python: command not found` (exit 127) before pytest started. The correct spelling — `python3 -m pytest backend/tests/test_docker_bcrypt.py -v` — is a property of the recorded answer, not of this test file, and must be fixed where that answer is recorded. This change cannot work around it in the tree.

## Risks

- **The container-level test has never executed.** No Docker daemon exists in this environment (consistent across every prior stage), so the build + in-image import assertions first run at a gate or host with Docker. If `docker compose build backend` itself fails there (pip/toolchain on python:3.12-slim — a candidate root_cause#114 judged unlikely, since bcrypt 4.x ships manylinux wheels for 3.12), the fix moves to the Dockerfile. The guard, by contrast, runs everywhere, so this pass adds verification actually exercised here.
- **The guard is textual and indentation-sensitive.** `lines.index("  backend:")` raises ValueError if the compose file's service indentation changes, failing confusingly rather than with the explanatory message. Compose's conventional two-space service indent makes this stable in practice, but it is real brittleness.
- **The exit-127 repro-command failure is not fixed by this change alone.** If the recorded repro-test-command still reads bare `python`, that check fails again for a reason outside the tree. It must be re-recorded as `python3 -m pytest backend/tests/test_docker_bcrypt.py -v`.
- **`pull_policy: build` requires a reasonably current Compose (v2).** On an older compose this key errors loudly at `up` rather than silently no-oping — but that failure mode was not observed here, and could not be.
- **Every-`up` rebuild is a deliberate trade** of startup speed for correctness; confined to the backend service (frontend build behaviour unchanged, lines 19–27).
- **Blast radius is unmeasured by the graph.** `impact` on both new test symbols returned `found: false` this pass (index holds no backend symbols; freshness reports the tree as indexed). Consumers that must not regress: the rest of backend/tests (host .venv, untouched), CI's install of requirements.txt (untouched), and `docker compose` itself (compose file semantically identical to the gate-accepted attempt-1 state).
- **Prior-attempt note errors, now corrected here:** the earlier change note cited the container-level test as living at docker-compose.yml lines 42–71 (it is at backend/tests/test_docker_bcrypt.py:41–71; the compose file has 31 lines) and attributed findings to run artifacts not supplied in this evidence; everything in this document is instead cited to files read directly in this pass or to artifacts present in the run record.
