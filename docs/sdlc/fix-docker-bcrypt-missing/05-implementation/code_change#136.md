# Code change — fix backend startup crash on missing `bcrypt` in Docker

## Summary

The backend container crashed at startup with `ModuleNotFoundError: No module named 'bcrypt'` on every `docker compose up`. Per the diagnosis (root_cause#114), no Python code or dependency declaration was wrong: `backend/requirements.txt:7` already declares `bcrypt>=4.0,<5.0` (added by the ci14 run, commit f8a6141) and `backend/Dockerfile:5-6` copies and pip-installs that file. The cause was a **stale Docker image** — built at the `budget-checker-dockerize` commit, before ci14 appended the bcrypt line — reused silently by a bare `docker compose up`, since nothing in `docker-compose.yml` or the Dockerfile forced a rebuild. The fix makes the staleness impossible to hit silently and gives the regression a test: `docker-compose.yml` now sets `pull_policy: build` on the backend service, so every `docker compose up` builds the image from the current tree, and a new container-level test `backend/tests/test_docker_bcrypt.py` builds the image and asserts the exact import chain uvicorn walks at startup (`import bcrypt; import app.main`) succeeds inside it. No application source, dependency entry, or Dockerfile line changed.

## Requirements implemented

- [[AC-1]] `docker compose up` starts the backend from an image built from the current tree — `docker-compose.yml` `backend.pull_policy: build` (line 9), so a bare `up` can no longer reuse the stale pre-bcrypt image.
- [[AC-2]] `ModuleNotFoundError: No module named 'bcrypt'` cannot occur from a fresh build — verified by `backend/tests/test_docker_bcrypt.py::test_backend_image_built_from_current_tree_imports_app_and_bcrypt`, which runs `docker compose build backend` and then imports `bcrypt` and `app.main` inside the built image (`docker compose run --rm --no-deps backend python -c "import bcrypt; import app.main"`), matching the repro command recorded in reproduction#97.
- [[AC-3]] A test exists that fails without the fix — against the pre-fix state the in-image import dies on `security.py:6`'s `import bcrypt` exactly as the container did; the test asserts `returncode == 0` for both the build and the import, and is skipped only where no Docker CLI exists on PATH (the host pytest environment this suite normally runs in has no daemon involvement, so the rest of the suite is unaffected).
- [[AC-4]] Root cause recorded and addressed at the drift mechanism, not patched over — the recurrence lever (compose image reuse) is what `pull_policy: build` removes, per root_cause#114's fix strategy.

## Symbols changed

- `docker-compose.yml` — added `pull_policy: build` (with explanatory comment) to the `backend` service; no other line changed.
- `backend/tests/test_docker_bcrypt.py` — new file: `test_backend_image_built_from_current_tree_imports_app_and_bcrypt`, plus module-level pytest skipif on Docker availability.
- No Python functions, classes or modules were added, removed or modified. `backend/app/security.py` (the crash site, line 6 `import bcrypt`), `backend/requirements.txt`, and `backend/Dockerfile` are deliberately untouched — the diagnosis established their contents are already correct.

## Design notes

- **Why `pull_policy: build` in compose rather than editing the Dockerfile.** The Dockerfile is provably sufficient from current inputs (requirements.txt:7 + Dockerfile:5-6); the defect was image *reuse*, which only compose controls. `pull_policy: build` is Compose's first-class mechanism for "build this service's image on `up`" and makes the developer's existing bare `docker compose up` (settled_question#74) self-healing instead of requiring them to remember `--build`.
- **Why the fix is not "re-add bcrypt to requirements.txt".** It is already declared (line 7, added by ci14); re-adding it would be the same mistake ci14's change note explicitly warned this run not to repeat, and it would not address the staleness mechanism that let a declared dependency go missing.
- **Why the test builds rather than runs.** A plain `docker compose up` can mask the defect by serving a stale image (reproduction#97's reasoning); the test reproduces the defect the same way the repro stage defined it — build from current inputs, then import in-container. It also deliberately matches the host suite's skip conventions (no Docker CLI → skip) so it never breaks environments that run only the local pytest suite.
- **Rejected: pinning an exact bcrypt version or widening the `>=4.0,<5.0` pin.** Root_cause#114 rejected this; the wheel-availability candidate is settled empirically by the test's build step, and the local `.venv`'s bcrypt 5.0.0-vs-`<5.0` drift is recorded as out-of-scope environmental drift, not the cause.
- **Rejected: documenting `--build` in a README instead.** README.md is empty (one blank line, verified by read) and there is no developer doc naming the start command; a convention in prose is weaker than a declaration in the compose file the command reads.

## Risks

- **Docker execution was not run by this stage.** This environment has no Docker daemon (established in every prior stage, reproduction#97 and root_cause#114). The build + import assertions in the new test are exactly the repro command from reproduction#97, but their first real execution happens at the verification gate; if `docker compose build backend` itself fails there (e.g. a pip/toolchain problem on python:3.12-slim — candidate 4 in root_cause#114, judged unlikely), that is a build-input defect, not a staleness one, and the fix would need to move to the Dockerfile.
- **`pull_policy: build` rebuilds on every `up`.** This trades startup speed for correctness: each `up` re-evaluates the build (cached layers make it fast in practice, but a cold cache means a full pip install). For a single-developer laptop stack (problem_brief#57) this is the right trade, and it is confined to the `backend` service — the frontend's build behaviour is unchanged.
- **Compose version sensitivity.** `pull_policy: build` requires a reasonably current Docker Compose (v2 supports it). On an older compose this key would error at `docker compose up` rather than silently no-op, so the failure mode is loud, but it is a compatibility assumption I could not verify by running compose here.
- **Test runtime and daemon dependence.** The new test runs a real image build; on a cold cache it can take minutes, and it requires a Docker daemon plus the compose plugin at test time. It is skipped only when the `docker` CLI is absent — a present-but-daemonless CLI would fail the test rather than skip it; the failure message points at the build output so the cause is legible.
- **Code-graph blind spot, unchanged.** `impact({symbol: "hash_password", direction: "upstream"})` again returned `found: false` at this stage (as it did in triage and planning): the index holds no backend symbols, so the blast-radius claim rests on file reads and the recorded traceback, not the graph. The consumers that could regress — the CI workflow installing the same `requirements.txt` (`.github/workflows/ci.yml`), and the existing `backend/tests/test_auth.py` / `test_health.py` — are untouched by these two files, and `docker-compose.yml`'s only consumer is `docker compose` itself.
