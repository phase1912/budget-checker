## Findings

1. **Low — frontend/src/pages/ReceiptsPage.tsx:11 — the size limit is hard-coded where the backend's is environment-tunable.** `const MAX_PHOTO_SIZE_BYTES = 5 * 1024 * 1024` mirrors `MAX_PHOTO_SIZE_BYTES = int(os.environ.get("MAX_PHOTO_SIZE_BYTES", ...))` at backend/app/routers/receipts.py:22. The decided fallback (baseline open question 1) is that the backend limit comes down if a 5 MB upload cannot fit the 10-second timeout; when that happens the frontend will accept a file the server refuses, showing a confusing server error on a file the UI called fine. There is no mechanism — no shared constant, no limits endpoint — that couples the two. Low severity only because the fallback has not yet fired and the failure is cosmetic, but it is the one place the feature's own decided contingency has no plan.

2. **Low — frontend/src/stores/ReceiptsStore.ts:49 — the bare `catch` in `loadPhoto` conflates "no photo" with "cannot read your photo".** `catch { // a missing photo is an ordinary state, not a fault (RCP-12) }` swallows every failure, including a 401 from an expired token (frontend/src/api/client.ts:58 throws for any non-ok status). The entry then renders as simply photoless. RCP-12 requires a missing photo to be ordinary; it does not require an auth failure to be indistinguishable from one. With one user and short sessions this is unlikely to bite, but it is a genuine boundary the requirement's wording does not cover, and the same catch is what motivated the test-environment stub in attempt 3 — evidence the catch is broader than its comment claims.

3. **Low — backend/app/routers/receipts.py:69 — `data = await file.read()` buffers the whole body before any size check.** The 5 MB limit is enforced only after the entire upload is in memory, so until the bound-upload question settles, the 10-second `TimeoutMiddleware` is the only guard on an arbitrarily large body. This is exactly baseline open question 1, recorded and with a decided fallback, not a new discovery — listed here so the reviewer of record knows it was seen in the code and not only in the documents.

4. **Low, document artifact (acceptance_spec#133), not code — RCP-13 still has no Gherkin scenario.** The frontend test "offers attaching a photo from the receipt's own entry" (frontend/src/pages/ReceiptsPage.test.tsx:60) does exercise the behaviour, and the code at ReceiptsPage.tsx:118-135 implements it, but the spec does not demand it. Recorded honestly since the baseline audit (settled_question#144); it remains open. Closing it is an amendment to the acceptance spec, not this diff.

No other findings. I specifically checked for and did not find: check-order leaks in the upload path (conflict → size → type, each refusing before any `db.add`, receipts.py:59-101); any unauthenticated photo URL anywhere in client.ts (RCP-16 holds — bytes always fetched with the bearer header, client.ts:50-66); any column added to `receipts` (models.py:57-74 adds only a relationship; `ReceiptPhoto` at models.py:80 is the new table, exactly the baseline's binding constraint); a weak assertion in the aborted-upload tests (the 4xx branch still fails loudly on a 2xx, test_receipts_aborted_upload.py:168-175); or anything in the diff the change notes did not declare.
